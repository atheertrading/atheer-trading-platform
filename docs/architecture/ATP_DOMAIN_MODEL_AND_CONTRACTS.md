# ATP-DOMAIN-001 — Canonical Trading Domain Foundation

**Status:** Implemented as a foundational contract slice; detailed trading semantics remain intentionally open.  
**Scope:** Provider-independent TypeScript domain contracts for identity, exact decimal values, instrument specifications, broker accounts, intent envelopes, risk decisions, lifecycle-policy validation, broker observations, execution events, reconciliation, and audit.

## 1. Authority and source reconciliation

This implementation follows the accepted target boundaries in `REPOSITORY_ARCHITECTURE.md`, the platform lifecycle and API/event principles, the user-directed domain-first delivery sequence, and the retrieved Library Q&A material.

The inspected knowledge base references accepted ADR-0004/ADR-0005 and ADR-0006/OOP, but their original texts were not present in the inspected Library archives. The implementation therefore does not infer or replace their contents. The original formal architecture archive reported in earlier records is also not present in the available Library folder. Q&A answers marked “Recommended” are treated as source guidance, not as proof of a formally approved detailed state machine.

## 2. Domain boundaries

The domain layer is provider-, transport-, persistence-, and UI-independent.

- It imports no HTTP framework, database driver, SwiftUI module, Capital.com SDK, or broker execution client.
- Broker adapters translate provider identities and observations into domain-owned contracts.
- Application services own command orchestration, risk evaluation, persistence, and execution sequencing.
- The domain layer contains no method capable of submitting a broker order.
- DEMO, SIMULATION, BACKTEST, and LIVE are explicit and never inferred from the broker identifier.

## 3. Identity and provenance

Internal identifiers are branded TypeScript types. Broker instrument identifiers remain broker-scoped and are always paired with broker identity and environment; an EPIC is never treated as a global instrument key.

Every broker-derived instrument specification, account snapshot, fill, and execution observation carries source identity, environment, provider event time, local receipt time, schema version, normalization version, and validation code.

Broker-confirmed account and execution facts remain authoritative. A local intent or order acknowledgement is not represented as a broker-confirmed fill.

## 4. Exact financial values and instrument specifications

Financial and quantity values are accepted as canonical base-10 strings only. The domain does not convert JavaScript binary floating-point numbers into financial values and does not apply implicit rounding.

Exact comparison and increment-alignment helpers use integer arithmetic internally. They do not select a universal rounding mode.

Instrument metadata keeps the following concepts separate:

- Price decimal precision.
- Actual price increment / tick size.
- Quantity precision.
- Minimum deal size and its unit.
- Maximum deal size and its unit.
- Quantity increment and its unit.
- Broker lot size.
- Contract size and underlying contract unit.
- Raw broker-specific constraints and source fields.

In particular, lot size is not silently equated with contract size, and price precision is not treated as proof of a valid tick increment. The provider's original units must be preserved. Missing or incompatible units fail validation; no default quantity or precision is synthesized.

A rounding policy reference may be attached to a specification, but no rounding policy is selected in this package. Any transformation that rounds price or quantity must be governed by a separately approved, explicit policy. A quantity below the broker minimum must not be rounded upward to force broker acceptance.

## 5. Order intent and centralized governance

All sources use the same immutable, versioned `OrderIntentEnvelope`:

- HUMAN.
- STRATEGY.
- ALGORITHM.
- POSITION_MANAGEMENT.
- RISK_MANAGEMENT.
- AI_AGENT.
- SYSTEM.

The envelope carries intent, command, correlation, and idempotency identities; account, instrument, specification version, environment, origin, UTC creation time, schema version, and typed payload. Payload operation/order-type codes remain extensible strings until the missing formal ADRs and original requirements are reconciled.

Intent creation is not authorization. A risk assessment is a separate immutable record bound to the intent and explicit policy version. Its outcomes are `AUTHORIZED`, `REJECTED`, or `HELD`. No source can convert an intent into broker execution by itself.

The Q&A recommends UUIDv7 generated by the backend execution boundary. Because the accepted original ADR text is unavailable and the current package has no ID-generation service, this slice defines strong identifier types but deliberately does not choose or implement an ID algorithm. The future application service must inject a backend-owned identifier generator.

## 6. Lifecycle and execution records

The domain provides a generic lifecycle-policy validator. A caller must supply an explicit initial-state set and transition map; transitions not present in that policy are rejected.

No concrete OMS order-state list or position-state list is frozen here. The Library's detailed Q&A contains recommendations, while the accepted architecture baseline explicitly leaves exact order states, order types, and transition semantics unresolved pending original formal specifications and broker contract validation.

Broker order records, position snapshots, fills, immutable execution events, reconciliation events, and audit events retain broker/source provenance and environment. Acknowledgement is not fill proof. Ambiguous execution outcomes require reconciliation before retry; no blind retry policy is encoded in this domain slice.

## 7. Testing

The deterministic Node test suite covers:

- Decimal canonicalization, comparison, and quantity-increment alignment without floating-point arithmetic.
- Instrument identity and broker/environment provenance.
- Separate price precision, tick increment, lot size, contract size, and quantity units.
- Invalid min/max and unit combinations.
- Broker account snapshot identity and provenance.
- Immutable intent envelopes and idempotency identity.
- Risk decisions bound to intent and policy version.
- Caller-supplied lifecycle transition policies.
- Execution-fill, reconciliation, and audit provenance.

This package does not implement PostgreSQL persistence, transactional outbox, broker order transmission, RiskEngine formulas, OMS state transitions, account synchronization, or LIVE execution.

## 9. Runtime shape validation at untrusted boundaries

Public domain constructors and validators must not assume that TypeScript interfaces guarantee the runtime shape of JSON-derived values. The domain now provides explicit record and array guards and applies them before dereferencing nested provenance, identity, instrument, account, intent, risk, lifecycle, broker order, position, fill, execution, reconciliation and audit structures.

Malformed object/array shapes fail with `DomainValidationError` and stable field-specific codes rather than incidental `TypeError` exceptions. This validation does not authorize an intent, change risk policy, infer missing financial values, or add broker execution capability.

The deterministic test suite covers null roots and nested records, arrays supplied where records are required, object-shaped arrays, and malformed quantity/price records.
